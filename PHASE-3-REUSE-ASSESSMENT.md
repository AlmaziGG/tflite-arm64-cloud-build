## Architecture Decision

`Runtime::from_path` и `examples/custom_runtime.rs` действительно позволяют явно открыть shared library. Но публичный Detector скрывает сырые признаки, квантует через FEATURE_SCALE и scale модели, копит нормированные float scores, ждёт полного окна и не реализует начальный счётчик ESPHome. Reset заново создаёт frontend и engine. Для трассировки, точного порога и проверки состояния потребовалось бы менять приватные части crate и добавлять Rust target/stdlib, tflite-c-rs и динамический загрузчик. Повторное использование одного native bridge сохраняет практический результат crate с меньшим числом ABI-зависимостей. Ни Cargo listener, ни bundled runtime в сборке не участвуют. На host и ARM кандидат компилируется из одного дерева vendor, oracle — из отдельно закреплённого C-дерева. Полное совпадение проверяет измерение байтов.

Кандидат принимает WAV или поток raw PCM. Один frontend/interpreter на сессию, 480 samples для первого кадра, затем 160 samples на кадр. Входной буфер 160 samples и очередь трёх векторов; последняя неполная группа не дополняется. Эталонный DSP использует 40 полос 125–7500 Hz, noise smoothing 10 / 0.025 / 0.06 / 0.05, PCAN 0.95 / 80 / 21, log shift 6. Преобразование saturate((x*256+333)/666−128) выполняется в 32 битах. Веса, SHA и минимальная SDK остаются закреплены. Для проверки эталонные признаки подаются отдельно в ту же PHASE 2B библиотеку, затем Python независимо рассчитывает окно, grace и события. Совместимость с TFLite Micro на ESP32 требует отдельного запуска.

**Оговорка о первом кадре.** В ESPHome 2025.2.0 `generate_features_for_window_` после цикла по `frontend_output.size` безусловно возвращает true. На шагах 1 и 2 размер нулевой, а локальный массив `audio_features` не инициализирован. Побитовое тождество неопределённому старту доказать невозможно. Сравнение охватывает каждый *выданный* кадр. Начальный счётчик −74 повышается до 0 на 74-м валидном кадре; проверка проводится на каждом кадре, включая промежуточные между Invoke. После события авторестарт соответствует новой сессии с пустой историей. Внутренний cooldown равен повторному прогреву; дополнительных секунд ожидания нет.

В отчёты попадают только производные синтетические данные, численные измерения и идентификаторы. ELF, сторонние исходники, модель, частные записи, OTA и трассы загрузчика остаются в рабочем каталоге CI. Латентность и память QEMU описывают эмулятор на runner. Для альтернативных бинарников, которые здесь не линкуются, минимальные версии glibc/libstdc++ не установлены. Для нашего ELF их проверяет production ABI-аудитор на каждой OTA.

## Проверенная поправка для Cortex-A35

При первой сборке GCC объединил операции с плавающей точкой при расчёте коэффициентов. На обеих OTA контрольные сборки с `-ffp-contract=fast` дали три отличия от x86 в целочисленных таблицах фильтра. Например, вес 211 получился 2470 вместо 2471. На Capsule-14 это изменило сырое значение 222 на 203 на кадре 99 (нумерация с нуля) смешанного сигнала. С `-ffp-contract=off` для нового runner все исследованные коэффициенты и выходные признаки совпали на обеих OTA. Каждая последующая проверка повторяет сравнение таблиц и требует точного совпадения рабочих признаков. Исторические SDK и бинарники PHASE 2B закреплены по исходным SHA. [Исходный прогон](https://github.com/AlmaziGG/tflite-arm64-cloud-build/actions/runs/45076428176) и [контрольный эксперимент](https://github.com/AlmaziGG/tflite-arm64-cloud-build/actions/runs/45076812972).

## Использование результата сборки

В подготовленном Linux userspace синтаксис команды — `runner MODEL TRACE CHUNK WAV...`. Для обычного режима TRACE равен `-`, CHUNK — `160`. Аргумент `-` вместо WAV включает потоковый PCM через stdin. Пример аргументов для внешнего spotter — `runner alisa_mww.tflite - 160 -`. Выход содержит одну UTF-8 строку «Алиса» на событие; диагностические счётчики пишутся в stderr. Несколько WAV в одном процессе используют общую неизменяемую модель и отдельные сессии. CLI отклоняет неподдерживаемые частоты, стерео, повреждённые RIFF и записи больше 256 MiB; raw stdin обрабатывается потоково.

Для воспроизведения служит workflow `phase3-audio-frontend.yml`. Golden-данные каждого синтетического fixture содержат сжатые строки по 120 байт (40 little-endian UINT16, затем 40 INT8). Первый кадр заканчивается на sample 480, последующие — через 160. `detection-results.json` хранит raw UINT8 по Invoke, сумму окна по каждому кадру и координаты событий в samples. Для модельной вероятности делитель 256, для среднего окна — 2550. Определения волн и seed находятся в `scripts/phase3.py::fixture`. У `question.wav` в локальном инвентаре неизвестен транскрипт. Для положительной речевой проверки потребуется согласованная запись с размеченным словом.
