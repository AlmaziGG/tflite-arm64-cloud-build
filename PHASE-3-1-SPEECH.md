# Проверка «Алисы» на человеческой речи

Baseline — `d77444bf4364446b4b3d9cb725a3bba5523d020c`. Файлы PHASE 3 собираются прежней командой. До эмуляции проверяются SHA-256 ARM64 ELF, модели и TFLite. Публичная ветка содержит только код, фиксированные метки и атрибуцию. Выборка зарегистрирована до первого прогона wake-word модели.

Аннотатор независимо вывел точное слово в обоих предложениях и падежную форму в n01. Тайминг автоматический и приблизительный. Для воспроизведения его Windows-декодер находится в wheel imageio-ffmpeg 0.6.0 с SHA `02fa47c83703c37df6bfe4896aab339013f62bf02c5ebf2dce6da56af04ffc0a`. Данные детектора при разметке не использовались. Два положительных примера принадлежат одному говорящему.

## Правила измерения

Учитывается окончание окна в координатах исходного PCM. Первый кадр заканчивается на sample 480, каждый следующий через 160. Кадр 74 — sample 12160 (760 мс); на нём разрешается срабатывание. После события и перезапуска frontend новый валидный кадр появляется через 480 samples. Из бинарных строк по 125 байт внешний анализатор заново проверяет stride, окно из десяти UINT8, строгую сумму >2295 и соответствие событий stdout. Значение модели — raw/256, среднее окна — sum/2550.

События сопоставляются с размеченными интервалами по времени, каждое используется один раз. Заранее выбран допуск к приблизительным границам 400 мс и максимальный дополнительный запаздывающий отклик 1 с после верхней границы. 400 мс — рабочий допуск, его статистическая погрешность отдельно не калибрована. Задержка равна времени события минус оценка конца слова и может быть отрицательной. p95 выводится только после 20 совпадений. Пустой знаменатель даёт null. Падежный контроль выделен для интерпретации возможного ложного события.

Каждый исходный WAV обрабатывается с чистым состоянием на обеих OTA. Проверяются восемь размеров/режимов подачи, отдельные процессы, повтор WAV в одном процессе, отрицательный затем положительный и последовательность всего набора. Отдельный эксперимент соединяет p01+n01+p01 в непрерывный PCM без сброса на стыках. События такого эксперимента не входят в исходные TP и FN. Если размеченное слово начинается до конца grace period, отдельный вариант добавляет 1 с нулевого PCM и сохраняет самостоятельный результат. Базовый порог во всех опытах 0,90.

## Воспроизведение и закрытые материалы

На подготовленном Linux x86-64 хосте нужны те же SDK, проверенная пара ELF PHASE 2B, QEMU, модель и две извлечённые OTA, что в workflow. После этапов подготовки `python3 scripts/speech31.py prepare` получает публичные источники и проверяет права и SHA. При отдельном разрешении владельца точный оригинал q01 можно положить в приватный `work/phase31-private/q01.wav`. `python3 scripts/speech31.py measure` повторяет проверку runtime, строгие ABI-аудиты и испытания. Полные бинарные трассы каждой OTA сохраняются локально в этой приватной директории. Полные хеши PCM, признаков, model scores и sliding sums доступны в агрегированных отчётах. Команды publish используются только со строго заданным списком файлов.

В GitHub Actions временный частный вход передаётся через environment secrets с разрешением только для точной feature branch. Base64 применяется для передачи байтов через секретное хранилище. Все семь частей обязательны при наличии хотя бы одной; SHA проверяется до записи файла. Секреты не передаются процессам сборки, входной материал не печатается, приватная директория удаляется шагом always(). Без доставки q01 стенд проверяет публичные образцы и показывает фактический состав. ZIP проверяется отдельным job по ID, SHA commit и ZIP, SHA256SUMS, точным схемам и пересчитанным метрикам.

Для расширения выбора предпочтительны три самостоятельных записи разных людей в mono PCM16LE 16 kHz, с 1–2 с тишины до и после слова. В отдельной закрытой разметке сохранить разрешение, точное содержание, примерные начало/конец слова и SHA файла. У обычных отрицательных примеров сохранить подтверждённое отсутствие слова. Наличие исходной записи само по себе не разрешает отправку в облако.

## Проверка пропусков

Первый прогон пропустил оба слова при нуле событий на отрицательных записях. Для публичных p01/p02 при пропуске выполняется независимый host oracle по всему исходному PCM. Его RAW/INT8-байты сравниваются с фактической трассой, а признаки независимо подаются в проверенную библиотеку через ARM64 replay. В отчёте остаются последовательности **скалярных** оценок и сумм окна только для этих публичных положительных записей. Для частной записи схема запрещает такие поля. Ни для одной записи артефакт не включает WAV, PCM или полную трассу признаков. Вариант с 1 с дополнительной тишины измеряется отдельно; его события не участвуют в базовых метриках. [Первый прогон](https://github.com/AlmaziGG/tflite-arm64-cloud-build/actions/runs/45079551973).
